**2026-11-07, implementing agent.** Done. `inviteFromRsvp` in `src/invites/invite.ts`, `inviteRepliedGuests` in `src/invites/repository.ts`, called by `updateEvent` when `inviteOnly` turns from off to on; `editTokenThroughInvite` in `src/rsvps/token.ts`; the `save` helper revalidates the invite and guest lists when `inviteOnly` changed; the Invites page's banner and per-row line; the hint's second sentence; `Invites.{inviteOnlyBanner,inviteOnlyNoMail,inviteOnlySettings,linkLetsIn}` in the three locales.

How it landed:
- **The switch** was built by 07 (`inviteOnly` on `EventInput`, `EventFormFields`, `parseEventSettings`, the checkbox, the link, `form.test.ts`). This ticket adds the hint's second sentence: "Guests who already replied are added to the list; those with an email prove it once."
- **Turning it on**: `updateEvent` reads `inviteOnly` in `before`, under the event's lock; when it goes from off to on, `inviteRepliedGuests(eventId, tx, now)` selects every reply of the event with `invite_id IS NULL`, inserts one invite each in one statement (`inviteFromRsvp(reply, now)`: name, email, phone, no letter, `rsvp_id`, `opened_at = now`; plus a fresh `generateInviteToken()`), then sets each reply's `invite_id` with one `UPDATE … FROM invite` joined on the new ids. Not capped by `MAX_INVITES`. Off deletes nothing; on again invites only replies that still have none. Since saving a reply takes the same lock first, a reply being written at that moment is written either before (and invited) or after.
- **The reply's token on the invite path** (controller's ruling 2): the reply's own edit token is not stored (only its hash), so `findInvitedRsvpOnThisDevice` cannot return it. `MyRsvp.token` is now `string | null`: `editTokenThroughInvite(invite.token, reply)` gives the invite's token when it hashes to the reply's `edit_token_hash` (a reply saved through the invite), else null (a reply made before its invite, i.e. these auto-invites). `saveRsvpAction` sets the `rsvp_` cookie only for a non-null token, so it is never set to a token that opens nothing; the device keeps finding the reply through its pass or invite cookie. `guestRsvp`'s edit link is the invite's link whenever there is one (always, on that path); `planRsvp`'s `mine.token` type follows. The comments above `findInvitedRsvpOnThisDevice`, `findRsvpOnThisDevice`, `MyRsvp` and the cookie in `saveRsvpAction` say this.
- **The Invites page**: when the event is invite-only, a banner under the explainer, the dashboard's attention fill (the verification banner's `Alert` shape, `role="note"` as it is not news): "Invite-only is on: only these people can open the invitation." and a link "Change it in the event’s settings" to `/events/[id]?sheet=settings`. On a site without mail, the line before the link is "This site cannot send email, so only the people here without an email can get in." Every row without an email, replied or not, says "Anyone with this link can open the invitation" in the attention colour.
- **The link opens the Settings sheet**: `EditorProvider` takes an optional `sheet`, and the editor page passes `"settings"` when `?sheet=settings` (nothing else is accepted).

Decisions and things to know:
- `inviteFromRsvp(reply, now)` takes the time it marks the invite opened, so it stays pure.
- A reply that stopped mail has a blank email, so its invite has none and its link alone lets its guest in; the row shows "Stopped email" from the reply's stop as before.
- Declined and pending replies are invited too: the spec says every reply.
- A guest who passed the gate just before the switch and whose save lands just after makes a reply with no invite on an invite-only event, and is then locked out. The window is one request long; not guarded (it would need `saveRsvp` to refuse a new reply without an invite on an invite-only event, which would also refuse a host replying to their own event).
- The no-mail banner sentence is not browser-tested: the site without mail is another Playwright project's (`app-no-mail`).
