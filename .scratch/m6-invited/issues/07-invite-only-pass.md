# 07: Invites: an invite-only event opens only to a device with a pass

**What to build:** The gate: on an invite-only event, the page and everything that opens an event by its slug open only to a host or to a device with a pass; the locked page lets an invitee prove their email with a code; a device with a pass has the invite as its identity. The setting itself is not yet offered to hosts (ticket 08 adds the switch and what turning it on does); this ticket's browser tests set `invite_only` through the repository or a test-only path, or wait for 08's switch, whichever the implementer finds honest, and say which.

Nothing of what turning it on does to existing replies, the hint's second sentence, the banner or the per-row warning (08).
- **The pass**: `inviteId.expiresMs.hmac`, the HMAC-SHA256 over `eventId:inviteId:expires` keyed by `AUTH_SECRET`, in hex; read back only with a UUID invite id, a numeric expiry still ahead, and a signature equal by `timingSafeEqual`. Set with `rsvpCookieOptions()` (a year, httpOnly, lax, secure on https). `inviteOnThisDevice(eventId)` (cached per request) returns `{ invite, pass }`: the pass's invite when the pass reads and `findInviteById` still finds it, else the invite cookie's (of this event), else nothing. A deleted invite therefore voids its pass on the next request.
- **Who is in**: `admitted({ pass, invite }) = pass || (invite && !invite.email)`. The gate gives it the device's invite: the pass's, else the invite cookie's, else the one its reply (the RSVP cookie's) is tied to. A device holding only the link of an invite with an email, or the edit link of a reply tied to one, is locked.
- **The gate**: `gateFor(event)` calls a `cache`d function keyed by `(id, state, inviteOnly)`, so the page, its metadata and a redraw ask once whatever object they hold. It looks the device's invite up only on an invite-only event and only for someone who does not host it. `eventPageFor`: a host sees the invitation; then a draft is not ready; then an invite-only event is locked to anyone not in; else the invitation (so a cancelled invite-only event's notice reaches only those in).
- **Identity by id**: `findInvitedRsvpOnThisDevice` loads the reply by `invite.rsvp_id` (`findRsvpById`); the RSVP-cookie path loads the tied invite (`findInviteById`) for `inviteToken`; `guestRsvp` gives `inviteUrl(inviteToken)` whenever there is one; `saveRsvp` still makes a new reply's edit token the invite's token, and carries `inviteToken` on the saved reply. `inviteCookieOptions()` is now `rsvpCookieOptions()` (a year). `/i/[token]` never sets `rsvp_`.
- **The locked page**: `page.tsx` renders `LockedPage` right after the "not ready" check, before the view is counted (a locked visit is not a view): a plain page with "A private invitation" (h1), "from {host}" (the owner's name, `event.hostName`), the form, and "Lost your link? Ask the host." The form's email is filled in and `readOnly` when the device's invite (cookie or reply) has one. - **`passAction`**: `consume("rsvp")`; for a post without a code `consume("mail")`; then the email's shape; then `findEventBySlug`; an event that is not (or no longer) invite-only, is a draft, or an instance without mail is redrawn as it now is. `findInviteByEmail` is case-insensitive (`lower(email) = lower($1)`, the first made). The code is kept under the invite's email as the host wrote it, or, for an address not on the list, under the typed address lowercased.

- **Metadata**: a draft is "not ready" for everyone, as before; a locked viewer gets `EventPage.lockedTitle` and `noindex` only; an invite-only event never gets a description, Open Graph, Twitter card or preview link, even for those in (title and `noindex` only).

Decisions and things to know:
- **An address not on the list is answered exactly as one on it**: `sendCode` with no `write` stores a code for it and sends nothing, so "Send it again" too soon, a wrong code, a code out of tries and an expired code all answer alike for both. Without that row, posting six codes, or waiting ten minutes, would tell an address on the list from one that is not.
- **A dead code is not replaced** on the locked page: a wrong code says "That code isn’t right."; expired, out of tries or never stored says "That code no longer works. Send it again for a new one." The RSVP form's automatic resend would have said "We sent a new one" to an address that got nothing, or within thirty seconds of the last (the known `codeTooSoon` quirk). So `InviteOnly.errors.codeWrong` carries no tries count.
- **The mail limit is consumed only on a post that asks for a code** (the first, and "Send it again"), before any lookup; a post with a code sends nothing and counts against `rsvp` alone. The ticket's wording put both before every lookup; the purpose (a refusal never tells) holds, and a guest entering a code no longer spends their household's mail allowance.
- **Without mail** the locked page shows no form, only the host's name and "Lost your link? Ask the host.": an invite with an email cannot get in on such an instance, as no code can reach it. The rule is not loosened; the operator docs say so. Not browser-tested (the no-mail app is another project's).
- **Gated beyond the ticket's list**: `sendReportAction` (`closed`), since its page is closed; `approvePhotoAction` (host-only already). Comments' three actions share an `opens(event)` helper.
- The device's invite for admission and for the locked page's email is the pass's, then the invite cookie's, then the reply's. A device with the cookie of an email invite and an RSVP cookie of a reply tied to a no-email invite is locked (one invite stands for the device).
- `saveRsvpAction` sets the RSVP cookie to `saved.token`, which on a device holding a reply only by its invite is the invite's token. For a reply made before its invite (08's case) that token opens nothing by itself; the device keeps finding the reply through its invite cookie or pass, so it is harmless, but 08 may want to leave that cookie alone.
- The redraw after a server action is not shared with the action's `cache`: `passAction` never asks the gate, so the redraw reads the new pass fresh.
