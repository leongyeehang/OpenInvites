# 04: Operator role, registration mode, and host invitations

**What to build:** The first account created on a fresh instance becomes the operator. The operator has an admin settings page where they choose the registration mode, Open or Invitation only, defaulting to Invitation only, and where they create, share, and revoke host invitations. In Invitation only mode, only someone holding a valid host invitation link can sign up.

**Blocked by:** 02 Host accounts

**Status:** done

- [x] The first account created on an empty instance is the operator; an environment variable can also promote an account by email at start. Exactly one operator in M1.
- [x] An admin settings page is reachable only by the operator; anyone else gets a not-found page.
- [x] Registration mode is stored in an instance settings table, defaults to Invitation only, and changes take effect immediately without restart.
- [x] In Invitation only mode the sign-up page explains that a host invitation is needed; a sign-up that arrives through a valid host invitation link proceeds and marks the invitation used; any other sign-up, including a new Google or GitHub account, is refused with a clear message.
- [x] The operator creates a host invitation, optionally addressed to an email, and gets a single-use link to copy; when SMTP is configured they can send it by email. Invitations expire after 14 days, can be revoked, and are listed as pending, used, or revoked.
- [x] The interface says "host invitation" everywhere and never "invite" (see CONTEXT.md).
- [x] Browser tests: the default mode blocks a second sign-up; a host invitation link lets it through and cannot be reused; a revoked invitation is refused; switching to Open allows any sign-up; a non-operator cannot open the admin page.

## Comments

**2026-09-24, implementing agent.** Done. Lint, type check, 277 unit tests (20 new, for the two pure rules this ticket adds), and the full browser suite (174 tests: 81 existing scenarios at 390px and desktop, the operator setup, 2 new scenarios at both widths, and 7 new scenarios on an instance of their own) pass against the production images on the Compose `test` profile: twice in a row on the local stack, whose database persists, and once on a separate Compose project started from empty volumes, as CI starts.

How it landed:

- One row holds the instance: `instance_settings` (migration `0013_operator_and_host_invitations`), whose boolean key can only be `true`, with the registration mode (`invitationOnly` by default, or `open`) and the operator's user id. The operator is that one column, so two operators cannot exist. The migration inserts the row and makes the earliest existing account the operator, so an upgraded instance has one and starts Invitation only.
- Every new host, by email, Google, or GitHub, passes `databaseHooks.user.create.before` in `src/auth/auth.ts`, which calls `admitNewHost` (`src/instance/admission.ts`). What can race is one conditional `UPDATE` each in `src/instance/repository.ts`: `claimEmptyInstance` (a sign-up that finds no accounts writes its email into `first_account_email`; of two at once only one can) and `redeemHostInvitation` (`used_at` is set only while it is null, not revoked, and not expired). The pure rule `signUpRefusal` (`src/instance/registration.ts`, unit tested) decides from what they found. A refusal is thrown as a Better Auth `APIError` with code `HOST_INVITATION_REQUIRED` or `HOST_INVITATION_UNUSABLE`: the email form shows it (`Auth.errors`), and a refused Google or GitHub sign-up comes back to `/sign-in?socialError=1&error=<code>`, which shows it (`Auth.signIn`). The `after` hook (`seatAdmittedHost`) makes the first account the operator, and the one `OPERATOR_EMAIL` names as `operatorEmailSeat` allows (next item).
- `OPERATOR_EMAIL` (`src/instance/env.ts`; revised in fix round 1, see below): that email may always sign up, whatever the registration mode, but signing up does not by itself make it the operator. With mail, its account becomes the operator, in place of whoever was, only once its email is verified: at creation when Google or GitHub report it verified, when its verification link is opened (`emailVerification.afterEmailVerification` in `auth.ts`), or at a start. Without mail, a new account with it takes the seat only while nobody holds it (`WHERE operator_id IS NULL`), and a start (`src/instrumentation.ts`, `promoteOperatorAtStart`) hands it over. The rule is `operatorEmailSeat` (`src/instance/registration.ts`, unit tested). README's Configuration section documents it, and a new "The operator, registration, and host invitations" section explains the rest, including to use an address other than `OPERATOR_CONTACT_EMAIL` and to unset the variable once your account is the operator.
- Host invitations (`host_invitation`): a 24-byte random token in the link, only its SHA-256 stored, so the link is shown to the operator once, right after it is made, with Copy link. With SMTP the create form offers "Email the link to this address"; without SMTP there is no such box. The link, `/host-invitation/<token>` (a route handler, like `/r/<token>`), leaves the token in an httpOnly, SameSite=Lax, one-hour cookie and redirects to `/sign-up`; the create hook reads that cookie, so it survives the round trip to Google or GitHub. States are a pure rule (`hostInvitationState`, `src/instance/host-invitation.ts`, unit tested): Used and Revoked are for good; a pending one past its 14 days is Expired. The list shows each with a badge, "Expires in N days" or "Used by <email>", and Revoke on pending ones.
- The sign-up page (`signUpNotice`, same pure module) says a host invitation is needed while registration is Invitation only, welcomes a visitor with a pending one (and fills in its email), and says a used, revoked, or expired one can no longer be used. An empty instance asks for nothing, so its first account can be made.
- The page is `/instance`, titled "Instance settings" (the glossary keeps "admin" for the operator out of the interface). It lives outside the `(host)` group, whose layout sends signed-out visitors to sign in; `requireOperator()` (`src/auth/session.ts`) calls `notFound()` for anyone else, in `generateMetadata` too, so the status, heading, and title match an unknown address. The host header moved into `src/app/(host)/host-header.tsx` so both use it; it shows "Instance settings" (an icon with a screen-reader name on phones) to the operator only.
- Tests: the main `app` runs in Open mode, set through the product: a Playwright setup project (`e2e/operator.setup.ts`) signs the test profile's `OPERATOR_EMAIL` account up or in and chooses Open on the instance settings page; `mobile` and `desktop` depend on it. `.env.development` sets the same `OPERATOR_EMAIL` so the dev loop works. What depends on the whole instance (first account, modes) runs in `e2e/registration.spec.ts` against `app-fresh` (port 3002) on `db-fresh`, a Postgres whose data is on tmpfs, in its own Playwright project, serially; its `beforeAll` recreates both containers (`docker compose --profile test up -d --force-recreate --no-deps --wait db-fresh app-fresh`), so each run starts from an empty instance on CI and locally. The operator works at desktop width there and the people signing up at 390px. `e2e/instance-settings.spec.ts` (both widths, on `app`) covers the operator's link and the not-found page for everyone else.

Decisions and things to know:

- Not the one-shot reset service the brief suggested: `docker compose up` re-runs an exited one-shot but leaves an unchanged running app container alone (tried with Compose 5.5.1, `depends_on.restart: true` included), so on the second local run the database would be dropped under a running `app-fresh`. The reset has to come from the test run itself; recreating a tmpfs Postgres empties it with no drop script.
- A host invitation the sign-up arrived with is used up whenever it still can be, even when the sign-up would have been let in anyway (Open mode, or `OPERATOR_EMAIL`), so the list says who used it.
- If the account creation fails after admission (only a database failure, or the same email signing up twice at the same instant), the invitation stays used, and on an empty instance the claim stays with that email, which may retry. `OPERATOR_EMAIL` is the way out of either.
- The operator can still delete their account; the instance then has no operator until `OPERATOR_EMAIL` names one and it restarts.
- "Pending" is also the glossary's word for an RSVP awaiting approval (M3); the brief asked for Pending here too.
- Checked by hand before fix round 1 (whose browser tests now restart instances and run one without mail): pointing `OPERATOR_EMAIL` at an existing non-operator account and restarting made it the operator and took the page from the previous one, and back again; with `SMTP_URL` empty the create form has no "Email the link" box and still shows the link. Racing 60 concurrent `claimEmptyInstance` calls, and 60 concurrent redemptions of one invitation, on a scratch database: exactly one won each, three times out of three.
- In the dev loop, `pnpm exec playwright test e2e/registration.spec.ts` needs the test-profile image (`docker compose --profile test build app-fresh`); its `beforeAll` starts the two containers itself.
