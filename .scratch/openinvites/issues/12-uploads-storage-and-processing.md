# 12: Uploads: storage and processing

**What to build:** A host uploads their own photo and uses it as the full-page background. The image is processed and sampled for brightness and colour, and stored behind one storage interface with local disk as the default and S3-compatible storage as an option.

**Blocked by:** 10 Design drawer: templates and knobs

**Status:** done

- [x] One storage interface with two implementations, local disk (default, a Docker volume) and S3-compatible, selected by environment (ADR-0003); application code never touches either directly.
- [x] The upload endpoint validates type and size against an operator-set maximum with a sensible default, re-encodes the image to a web format, produces a large background size and a preview-card size, and discards the original.
- [x] The server samples the image's average luminance and a dominant accent colour and stores them on the upload record; the theme's auto accent and auto text tone use them.
- [x] The host can enter alternative text for the upload, used on the page.
- [x] The drawer's Upload button works: after an upload the background switches to it, with the Background or Poster choice appearing beside the thumbnail (Poster becomes functional in ticket 13).
- [x] Replacing an upload or deleting the event removes the stored files.
- [x] A CI smoke test runs the S3 implementation against a local S3-compatible container: upload, read back, delete.
- [x] Browser test: upload a light image and see the text tone flip to dark automatically; upload over the size limit and see a clear message. Unit tests: luminance and accent sampling on fixture images.

## Comments

**2026-09-23, implementing agent.** Done. Lint, type check, 225 unit tests, the S3 smoke test (`pnpm test:s3` against the Compose `s3` profile), and 152 browser tests (76 scenarios at 390px and desktop) pass against the production image on the Compose `test` profile. The uploads spec also passed with the app itself on S3 storage (dev server pointed at the `s3` profile's container). The CI step is wired but has not run in GitHub Actions, since nothing is pushed.

How it landed:

- **Storage (ADR-0003):** `src/storage/storage.ts` is the interface (`put`, `get`, `delete` on flat keys) and `getStorage()`, which picks `disk.ts` (default) or `s3.ts` from `config.ts`. Nothing else touches the directory or the bucket. The S3 client is `@bradenmacdonald/s3-lite-client` (MIT, no dependencies, about 8 kB gzipped, maintained since 2021, 1.0 in August 2026), with path-style requests. `@aws-sdk/client-s3` would have brought 56 dependencies for three calls.
- **Upload endpoint:** `POST /api/events/[id]/upload`, a route handler with the picture's bytes as the body. A server action's body limit is fixed at build time (1 MB unless `next.config.ts` raises it), while `MAX_UPLOAD_MB` is read at start, so the handler reads the body up to the limit itself and stops there. It checks the Origin against `BASE_URL` (as Next.js does for server actions), the session, and that the event is the host's. The drawer checks the size first and says so without sending the file.
- **Processing (`src/uploads/`):** `validate.ts` (pure) reads the type from the file's first bytes (JPEG, PNG, WebP, AVIF; SVG, GIF, HEIC and the rest never reach the decoder), the size against the limit, and the pixel count from the header (50 MP at most). `process.ts` uses `sharp` (the library Next.js uses, already in the tree): EXIF orientation applied, transparency onto white, sRGB, then re-encoded with no EXIF, XMP, IPTC or ICC profile, so a photo's location never reaches a guest. Renditions: `background.webp` (at most 2048 px on its long side, never enlarged) and `card.jpg` (1200x630, because Satori in `next/og` reads PNG, JPEG and GIF but not WebP). The original is not kept.
- **Sampling (`sample.ts`, pure):** average luminance, measured the way `backgrounds.ts` measures the curated ones. The accent is the dominant hue band (weighted by chroma squared, ignoring greys), lifted to 0.70–0.85 HSL lightness on a dark picture and deepened to 0.30–0.45 on a light one, as the curated accents sit. A picture with no colour gets a neutral. The lightest and darkest points are taken as the glass sees them: `process.ts` scales the picture as it would cover a 1920x1080 screen (the largest of the measured viewports, which the other four are all smaller than), works at a quarter of that size with the 24px blur as 6px, and `measureBackdrop` applies each tone's scrim. The upload record stores all four values; `resolveTheme` builds a photo `Background` from them, so the auto accent, the auto text tone and `legibility.ts` all use the measurements. `UNMEASURED` is gone. A dark photo keeps the light 10% frost instead of the smoked worst case.
- **Upload record:** table `upload` (migration `0011_uploads`), unique per event, with `alt_text`, `luminance`, `accent`, `lightest`, `darkest`. The id comes from Postgres (`select uuidv7()`) before the files are stored under it. The row is written only after the files exist. Replacing happens in one transaction under the event's row lock: the old row goes, the new one comes in, and the theme is changed through `applyChange(theme, { knob: "uploadId", value })`. The old files are removed after commit.
- **Theme:** a new `KnobChange` `{ knob: "uploadId", value }` sets `backgroundId: null`, `uploadId`, `uploadMode: "background"`, puts the accent back on auto, and marks the template dirty. `parseThemeChange(raw, upload)` accepts only the event's own upload id (`changeThemeAction` looks it up). A curated background leaves `uploadId` in place, so the tile stays in the gallery.
- **Drawer:** the Upload button, then (once there is a picture) its thumbnail with a "Use it as" row: Background, and Poster disabled with "Coming soon" (the same `Choice` + `Badge` as Broadsheet and Thread). Replace sits under the row, followed by "Describe your picture" (alt text, saved on blur, Enter or Escape through `describeUploadAction`). A "Your picture" tile is last in the Background gallery. Problems appear as an alert under the button, with messages from `uploadProblems.*`.
- **Page:** the upload is painted like a curated scene (cover, tone scrim, fade at the foot). Its description is a `role="img"` element with the host's text as its label, at the end of the poster card (`background-description.tsx`), so a screen reader meets it once, with the invitation. Nothing is said when the description is empty. Guests are sent the upload only while it is the background: one the host set aside is not in their page at all (a browser test checks this).
- **Serving:** `GET /uploads/<id>/<file>` reads through the storage interface for either backend, with `Cache-Control: public, max-age=31536000, immutable` and `nosniff`. It returns 404 for unknown files, non-UUID ids, and once the picture is replaced or deleted.
- **Preview card:** when the theme shows the upload, `/e/<slug>/preview.png` draws its `card.jpg` rendition (as a data URL) under a gradient of the tone's base colour.
- **Deleting:** every event deletion goes through `removeEvents` in `events/repository.ts`: lock the events, delete their upload rows and the events, then remove the files. Better Auth's `deleteUser.beforeDelete` calls `deleteHostEvents` after the password has been checked, so deleting an account removes its pictures too (browser tests: the rendition URL 404s after replace, event delete and account delete). A file that cannot be removed is logged and left, not allowed to undo the delete.
- **S3 smoke test:** `src/storage/s3.smoke.ts` stores 300 kB, reads it back, deletes it, and checks that a wrong secret is refused, so the round trip proves the signing. It runs under `vitest.s3.config.ts` (`pnpm test:s3`), which `pnpm test` does not include. The server is Versity Gateway (`versity/versitygw:v1.8.0`, Apache-2.0, 31 MB image, released monthly, checks SigV4 signatures) as the Compose `s3` profile, with its bucket as a directory made at start. MinIO's community edition is in maintenance mode, Adobe S3Mock does not check signatures, and Garage is AGPL. CI runs it after the unit tests and tears the profile down with the test stack.

Environment variables (new, for ticket 19 to document):

- `STORAGE_BACKEND`: `local` (default) or `s3`.
- `UPLOADS_DIR`: local storage's directory, default `uploads` under the working directory, which is `/app/uploads` in the image. The directory is made and owned by `node` in the image; mount the uploads volume there.
- `S3_ENDPOINT` (required for s3, e.g. `https://s3.eu-central-1.amazonaws.com`), `S3_REGION` (default `us-east-1`), `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` (all required for s3). The bucket can stay private.
- `MAX_UPLOAD_MB`: default 10 (MiB), decimals allowed; anything not a positive number stops the app at start, as a bad storage setting does (`instrumentation.ts`).

Decisions and things to know:

- `sharp` is now a direct dependency (it was only Next.js's optional one). Version 0.35 has no install script; pnpm installs the prebuilt libvips for the platform in the Dockerfile's deps stage, and the standalone output carries `@img/sharp-linuxmusl-x64` (checked inside the image).
- Processing cost, measured locally: a 48 MP JPEG takes 0.57 s and about 93 MB extra; a 50 MP PNG peaks at about 180 MB extra. The two renditions and the two rasters sampled for the theme are made in parallel, one decode each.
- A transparent picture is flattened onto white. That is a guess about the page it was made on, and a dark logo on a transparent ground stays readable.
- Immutable caching means someone who already loaded a deleted picture may still have it in their browser cache. The server no longer serves it.
- If Better Auth fails after `beforeDelete` has run, the host keeps an account with no events. There is no way to fold both into one transaction from outside Better Auth.
- A theme change for the upload racing a replacement could leave the theme naming the old id. `resolveTheme` then shows the default background until the host picks again; nothing breaks.

Left for later tickets or noted:

- **For ticket 13:** the background rendition keeps the picture's natural proportions (fit inside, no crop). Uploads made before 13 have no poster rendition, and their originals are gone, so `background.webp` can stand in as the poster, or the poster rendition can be added to `RENDITIONS` (`renditions.ts`; `files.ts` stores and removes every name listed there). The Poster choice is the disabled `Choice` in `design-panel.tsx`, and `showingUpload` there requires `uploadMode === "background"`. `resolveTheme` currently treats an upload in either mode as a photo background. In poster mode the poster's `<img alt>` should carry `altText`, and `BackgroundDescription` should not repeat it. Poster mode's darkened, blurred backdrop needs its own extremes: `measureBackdrop` applies the page's scrims.
- **For ticket 18:** rate-limit `POST /api/events/[id]/upload` (it holds up to `MAX_UPLOAD_MB` in memory, plus the decode above). `GET /uploads/<id>/<file>` is unauthenticated, protected only by the unguessable UUIDv7. The endpoint answers 413 on `Content-Length` before reading the body, and a browser may report that as a network error; the drawer never sends an oversized file.
- **For ticket 19:** document the variables above; the uploads volume at `/app/uploads` belongs in the production Compose file and in the backup notes (or the bucket, with S3). Check that the arm64 image carries `@img/sharp-linuxmusl-arm64`. Requests to S3 are path-style, which AWS, R2, B2, Wasabi and Garage accept. A provider that insists on virtual-hosted style would need `pathStyle: false` in `storage/s3.ts`.

The sizes use `{max, number}`. The drawer's "Describe your picture" field and the page's `role="img"` description were not audited with a screen reader.
