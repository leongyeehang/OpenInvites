# 18: Operator hardening: rate limits, legal pages, analytics

**What to build:** The instance is safe to expose to the internet: rate limits with clear messages protect every form and every slug, the operator's privacy policy and terms are published, an optional analytics snippet loads only when set, and the operator contact is shown where it helps.

**Blocked by:** 07 Guest RSVP flow, 04 Operator role, registration mode, and host invitations

**Status:** done

- [x] Rate limits behind one interface with an in-memory implementation (single application container assumed in M1) on sign-up, login, password reset, RSVP submission, uploads, and event page requests by slug, with unknown slugs counted so that slugs cannot be guessed; limits are configurable and lowered in the test profile.
- [x] A guest or host who is throttled sees a friendly "too fast, try again shortly" message, never a blank error.
- [x] Privacy policy and terms pages are rendered from operator-provided Markdown (a mounted path or environment contents) with shipped placeholders that make the gaps obvious; both are linked from every page footer.
- [x] An analytics snippet from one environment variable is injected into every page's head only when set; when empty, no script tag exists.
- [x] The operator contact address appears on the legal pages and on the "contact the operator" reset screen.
- [x] Browser tests: a burst of RSVP submissions is throttled with the message; a burst of unknown-slug requests is throttled; legal pages render the operator's text; the snippet is present or absent according to the environment.

## Comments

**2026-09-24, implementing agent.** Done. Lint, type check, 309 unit tests (28 new: client address, limiter window, limit settings, legal-page source, Markdown rendering), and the full browser suite (198 tests, 21 of them new: 11 scenarios, most at both widths) pass against the production image on the Compose `test` profile.

How it landed:

- **One RateLimit module (`src/rate-limit/`), one store, one client-address rule.** `client-address.ts` (pure): with `TRUSTED_PROXY_HOPS` proxies in front (default 1, the deployment package's Caddy), the client is the `X-Forwarded-For` entry that many places from the right, the one the outermost trusted proxy appended; entries further left were written by the client and are never believed; fewer entries than hops means the leftmost; an entry that is not an IP address, a missing header, or `TRUSTED_PROXY_HOPS=0` gives no address. `window.ts` (pure): a fixed window per client and limit, opened by its first request; a refused request is not counted and does not push the window back. `config.ts` (pure): each limit is one variable, a count per window such as `60/10m` (s, m or h); a value it cannot read stops the app at start (`instrumentation.ts`). `rate-limit.ts`: the `RateLimitStore` interface (async, so a shared store can replace it) and its in-memory implementation, which forgets finished windows once a minute; `consume(limit, headers)` is the one entry point everything calls. Requests with no client address share one allowance per limit: with `TRUSTED_PROXY_HOPS=0` the log says so once at start, otherwise the first such request says so.
- **The proxy and the app share the store.** `src/proxy.ts` is bundled apart from the app but runs in the same Node process, so the store hangs off `globalThis` (`Symbol.for("openinvites.rateLimit")`). Checked in the production image: five opens of a host invitation link used up the sign-up allowance for a following `POST /api/auth/sign-up/email`.
- **What counts where** (as first landed; fix round 1 below widens it). The proxy counts every GET and HEAD under `/e/` against the event page limit, before any route sees it: the page, `preview.png` and `calendar.ics`, for a real, retired, or never-issued slug alike, so links cannot be found by trying them. It also counts `/host-invitation/<token>` against the sign-up limit (ticket 04's note). Server actions posted to an event page are not page requests, so the host's Design drawer is never throttled; `saveRsvpAction` counts each RSVP before it looks anything up (it is otherwise an oracle for whether a slug exists). The upload route counts after the Origin check and before reading the body. Sign-up, sign-in, and password reset (asking for the link, and setting the new password) are counted in Better Auth's `hooks.before` (`src/auth/auth.ts`), which runs both for the forms' server actions (direct `auth.api` calls) and for requests to `/api/auth` itself.
- **Better Auth's own limiter is off, and so is its reading of client addresses** (`rateLimit.enabled: false`, `advanced.ipAddress.disableIpTracking: true`). Its limiter could not take a hop count (only CIDR lists), would have counted `/api/auth` requests apart from everything else, and never saw the forms at all: server actions call `auth.api` directly, which skips it. With tracking off, new sessions record no IP address (`session.ip_address` is empty); nothing in the app ever showed it. `e2e/hosts.ts` no longer sends its own `X-Forwarded-For` in `verifyEmail`; see the fixture below.
- **Refusals say "You’re going too fast. Try again shortly."** A page request (anything the proxy counts) is rewritten to `/too-fast`, a real page in the root layout with its footer, as 429 with `Retry-After` and `no-store` (checked in the production image). A form shows the same sentence where its other errors go: the RSVP flow's alert (`Rsvp.errors.tooFast`, the guest keeps their place and their saved RSVP stands), the auth forms' `FormOutcome` (`Auth.errors.TOO_MANY_REQUESTS`, from the hook's `APIError` code), the Design drawer's upload alert (`DesignDrawer.uploadProblems.tooFast`, on a 429). A direct `/api/auth` request gets Better Auth's JSON 429 with `Retry-After`.
- **Legal pages (`src/legal/`, `/privacy`, `/terms`).** `source.ts` (pure): `PRIVACY_POLICY_MARKDOWN` or `PRIVACY_POLICY_FILE`, and `TERMS_MARKDOWN` or `TERMS_FILE`; neither means the shipped placeholder; both for one page stops the app at start, as does a file that cannot be read. A mounted file is read on every request, so an edit shows without a restart. `markdown.ts` renders with markdown-it (`html: false`): raw HTML is shown as text and javascript:, vbscript:, file: and data: addresses make no link (unit tests, each checked by a mutation). `placeholders.ts` says plainly that the operator has not published the page, which variables replace it, and what such a page usually covers on an instance, in the glossary's words (what hosts and guests leave behind, the four cookies, network addresses held in memory by the limits). Each page shows `OPERATOR_CONTACT_EMAIL` under the text ("Questions? Contact the operator of this instance at ..."), or says there is none.
- **The footer** (`src/components/page-footer.tsx`) links both pages from every page: the root layout puts it under everything. A themed event page carries its own inside `ThemedPage`, on the veil in the theme's secondary text (the style of the RSVP flow's "not taking RSVPs" note), and the plain one steps aside through a `themed` custom variant (`body:has(.event-page)`), so there is only ever one. Not-found, retired-link and not-ready pages are unthemed and get the plain one.
- **Analytics (`ANALYTICS_SNIPPET`).** Unset, the root layout renders no `<head>` element of its own and no script of any kind. Set, the head's content is the snippet as given, led by a one-line marker script of ours (`src/components/analytics.ts`); `suppressHydrationWarning` because the head then also holds Next.js's own tags. A page that ends in `notFound()` (an unknown event link, the instance settings for anyone but the operator, a mistyped host address) is sent by Next.js as its error-recovery document and built in the browser, and scripts arriving that way never run: React cannot catch `notFound()` during server rendering, which predates this ticket. There the marker has not run, so `AnalyticsFallback` swaps each of the snippet's scripts for a copy made as the parser would (attributes, text, in order) and runs it once. Without it, the not-found page ran none of the snippet (checked by mutation).
- **Malformed host event ids.** `findHostEvent` finds nothing for an id that is not a UUID, so `/events/<anything>`, `/share` and `/guests` give the not-found page with 404 instead of a Postgres error and 500 (browser test, which failed with 500 before the fix).
- **Browser tests.** `e2e/rate-limits.spec.ts`: forty guesses at event links go through as 404, the next gets the 429 page with its heading, title and Retry-After, and so do `preview.png` and `calendar.ics`; an address written in front of the proxy's changes nothing; another address is not held up; the sixth RSVP in a minute shows the message in the sheet, the guest's typing stays and their earlier RSVP stands; the sixth sign-in shows it in the form; the fourth upload shows it in the drawer. `e2e/legal-and-analytics.spec.ts`: on `app`, the placeholders with the contact address, no script in any head that did not come from the app, and the footer on the host's pages, before signing in, and on an event page, where there is one footer and its links are the colour of the invitation's own secondary text; on `app-social`, the privacy policy from the environment (headings, bold, and `<b>` shown as typed) and the terms from a mounted file (`e2e/legal/terms.md`), and the snippet in the head of five pages, including an event page and a not-found one, having run once on each. `e2e/registration-without-mail.spec.ts`: the no-mail reset screen and both legal pages show the operator's address (`app-no-mail` now sets `OPERATOR_CONTACT_EMAIL`). `e2e/events.spec.ts`: the malformed ids.
- **Every test has an address of its own** (`e2e/test.ts`): an `extraHTTPHeaders` fixture sends a random private `X-Forwarded-For` from every context and request a test makes, as the proxy would, so parallel tests never share an allowance. Every spec now imports `test` and `expect` from `./test`. The `app` service and `.env.development` set the low limits below; the heaviest existing test used 20 of its 40 event page requests.

Decisions and things to know:

- **Defaults are for people, some of whom share an address** (an office, a phone network's NAT): event pages 120 a minute, RSVPs 60 per 10 minutes, uploads 20 per 10 minutes, sign-ups 10 an hour, sign-ins 10 per 15 minutes, password resets 10 an hour, mail 10 an hour. A team answering one invitation from the office together should never be turned away; a script flooding a guest list, an inbox, or a password still is.
- **A fixed window** can let up to twice a limit through across the moment one window ends and the next begins. Simple and predictable, and the limits are per address anyway.
- markdown-it 15 (MIT, six small dependencies, its own types, released this month) was chosen over marked (no switch for raw HTML, so a sanitiser would be needed on top), micromark (about twenty packages) and react-markdown (the unified stack).
- The placeholders are English Markdown in `placeholders.ts`, not translation strings: they stand in for the operator's own text, which is shown as written.
- `/too-fast` can be opened directly (200), and says the same thing. Harmless.

**2026-09-24, implementing agent, review fix round 1.** The review found three gaps: posts under `/e/` were not counted (Next.js draws a dynamic page for any POST), mail-sending endpoints and password checks lost their limits when Better Auth's limiter went off (anyone could loop verification emails to a stranger's unverified address without signing in), and IPv6 clients were keyed by full address with no cap on the store. Lint, type check, 319 unit tests (10 new, test first), and the full browser suite (208 tests, 10 new) pass against the production image on the Compose `test` profile. Three commits: `f4f15de`, `7ec2344`, `3298535`.

- **Every request under an event link counts** (`src/proxy.ts`), whatever its method, except a POST naming a server action in `Next-Action`: that is the page's own form (RSVP, Design drawer), whose answer must be the action's own, with its limit and message. Checked in Next.js's code: an action it does not know is answered with a bare 404 before any page is drawn; an action belonging to another page (the language switcher's, say) is forwarded to that page, and a forwarded action never draws the event page (also with a client-set `x-action-forwarded`); a URL-encoded one gets the generic not-found tree. But one of the event page's own actions that changes something (revalidates, refreshes, or sets a cookie) is answered with the page it was posted to drawn again, whatever that address's slug: so the page counts its own redrawing (`redrawAllowed` in `e/[slug]/page.tsx`, cached so page and metadata count once) against the event page limit, for anyone but the event's host (whose drawer redraws at every change), and past the limit draws "too fast" (`src/components/too-fast.tsx`, shared with `/too-fast`) whatever the slug. This closes a signed-in host probing other slugs through their own drawer actions, and RSVP redraws.
- **`removeRsvpAction`** counts against the RSVP limit before any lookup and returns `{ error: "tooFast" }`; the confirmation shows it under its links.
- **Mail limit, `RATE_LIMIT_MAIL` (10/1h).** Counted with the other limits in `hooks.before` (`limitsByEndpoint` in `auth.ts`, now a list of limits per endpoint, `consumeAll` stops at the first refusal): `/sign-up/email` (with mail), `/send-verification-email`, `/change-email`, `/request-password-reset` (still under the password reset limit too); and in `createHostInvitationAction`, before the invitation is made, when it is to be emailed (`Instance.invitations.tooFast`).
- **Password checks count as signing in:** `/change-password`, `/delete-user`, `/verify-password`, and `/sign-in/social` (covered by Better Auth's old "/sign-in*" rule). A refused social click comes back to `/sign-in?socialError=1&error=TOO_MANY_REQUESTS`, which the page shows (`Auth.signIn.TOO_MANY_REQUESTS`).
- **Client key (`src/rate-limit/client-key.ts`, was `client-address.ts`).** After choosing the entry, an IPv4-mapped IPv6 address (`::ffff:a.b.c.d`, either spelling) becomes its IPv4 address, and any other IPv6 address is keyed by its /64, however it is written (compression, case, leading zeros, a zone, an IPv4 tail).
- **Store (`WindowTable` in `window.ts`).** One table per limit, in the order windows opened; windows that are over are always at the front, so each request forgets just those (nothing is walked once a minute any more); past `MAX_CLIENTS_PER_LIMIT` (20,000, about 4 MB a limit at about 200 bytes a window, measured) the oldest are forgotten first. The store interface is now `hit(limit, client, rule, now)`.
