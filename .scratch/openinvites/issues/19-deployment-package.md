# 19: Deployment package

**What to build:** An operator goes from a fresh machine to a running OpenInvites instance using only the documentation, with images built for amd64 and arm64 and published on every tagged release.

**Blocked by:** 12 Uploads: storage and processing, 18 Operator hardening: rate limits, legal pages, analytics

**Status:** done

- [x] A multi-stage Dockerfile produces a small, non-root image from Next.js standalone output.
- [x] A production Compose file runs the app and a pinned Postgres 18 image with health checks on both, named volumes for the database and uploads, and an environment file that documents every variable including SMTP, Google and GitHub, storage backend and S3 settings, upload limit, analytics snippet, legal page sources, and operator contact.
- [x] The image does not terminate TLS; an example Caddy configuration provides automatic HTTPS in front of it.
- [x] CI builds amd64 and arm64 images on tagged releases and pushes them to GitHub Container Registry and Docker Hub with semantic version tags and a moving latest tag.

How it landed:

- **`deploy/`** is the deployment package: `compose.yaml` (project `openinvites-instance`, so it never mixes with the root file's `openinvites` dev/test project and its volumes), `.env.example`, `Caddyfile`, `smoke-test.sh`. The operator edits only `.env` (and an optional `compose.override.yaml`), so a release's `compose.yaml` can replace theirs. `.env` is both Compose's interpolation file and the app's `env_file`; `BASE_URL`, `AUTH_SECRET` and `POSTGRES_PASSWORD` are required with `${VAR:?...}`, so `docker compose up` refuses to start without them. `DATABASE_URL` is built from `POSTGRES_PASSWORD` in `compose.yaml`.
- **Services:** `app` (image from `OPENINVITES_IMAGE`, default `ghcr.io/leongyeehang/openinvites:latest`), published on `127.0.0.1:${APP_PORT:-3000}` only, with the `uploads` volume at `/app/uploads` and a health check on `/api/health`; `db`, `postgres:18.6-alpine` (the newest 18 minor; 18.5 was never tagged), with `db-data` and `pg_isready`; `caddy`, `caddy:2.11-alpine`, behind the `caddy` profile, which `.env.example` turns on with `COMPOSE_PROFILES=caddy`.
- **Caddy uses `network_mode: host`.** Through Docker's port forwarding an IPv6 visitor reaches a container on an IPv4-only Compose network as Docker's own gateway address, so every IPv6 visitor would share one rate-limit allowance. On the host network Caddy sees real addresses and reaches the app on the loopback, and the same `Caddyfile` works for a Caddy installed on the machine. The cost: the bundled Caddy needs Docker Engine on Linux (the docs say so; Docker Desktop users try it locally or bring their own proxy). The site address is `{$BASE_URL}`, one source for both the app and the certificate; a trailing slash would make Caddy serve only `/`, so the docs and `.env.example` say "no trailing slash". A commented `trusted_proxies` block for a CDN holds a placeholder that Caddy refuses until real ranges replace it.
- **Checked by hand on this machine** with the Caddy profile (`BASE_URL=https://localhost:8443`, Caddy's local CA): health through Caddy; six requests to an unknown event link through Caddy, each with a different forged `X-Forwarded-For`, and the sixth was refused (limit set to 5); the same seven straight to the app's loopback port all went through, which is why the port must stay on the loopback. Then, on that stack: signed up a host, ran `docker compose exec app node scripts/reset-password.mjs host@example.org` as documented, deleted the host's sessions with the then-documented `psql` line (gone in fix round 1, below: the command now does it), backed up with `pg_dump` and `tar` exactly as `upgrade-backup.md` says, `down -v`, restored per the doc (db only, `pg_restore`, `docker compose run ... tar -x` into a fresh `uploads` volume, owned by `node`), and signed in with the temporary password on the restored instance, which was still the operator. Also: a bad `MAX_UPLOAD_MB` leaves the app unhealthy with the variable named in `docker compose logs app`, and an unreachable SMTP server is logged there (`ENOTFOUND`). Idle memory: app 55 MB, Postgres 45 MB.
- **Dockerfile:** OCI labels (title, description, source, `licenses=AGPL-3.0`) on the runner stage; the release workflow adds version, revision and created. Nothing else changed: the image is 75.6 MB compressed (the `node:22-alpine` base is 60.8 MB of it), runs as `node` (uid 1000). `.dockerignore` now leaves out `deploy/`.
- **arm64 `sharp`:** the lockfile carries `@img/sharp-linuxmusl-arm64` with `cpu: [arm64]`, `libc: [musl]`. Simulated without QEMU: `pnpm install --frozen-lockfile` in `node:22-alpine` with `supportedArchitectures` set to linux/arm64/musl installed exactly `@img/sharp-linuxmusl-arm64`, `@img/sharp-libvips-linuxmusl-arm64`, `@next/swc-linux-arm64-musl`, the Tailwind oxide and lightningcss arm64-musl builds, and no x64 ones. A native arm64 build (QEMU in CI, or a real machine) has pnpm's default, the running platform, so it selects the same; the standalone output then traces whatever `@img/sharp-*` exists, as it traced the x64 one here. The smoke test loads `sharp` inside the container, so a missing arm64 binary fails the release's arm64 smoke job.
- **CI:** `ci.yml` gains `workflow_call`, and its `push` trigger is now branches only, so a tag does not run the suite twice. `release.yml` on `v*.*.*`: `checks` (`uses: ./.github/workflows/ci.yml`), then `publish` (QEMU, Buildx, login to GHCR with `GITHUB_TOKEN` and Docker Hub with the `DOCKERHUB_USERNAME`/`DOCKERHUB_TOKEN` secrets, metadata-action tags `{{version}}`, `{{major}}.{{minor}}`, `{{major}}` except for 0.x, and `latest` except for pre-releases, build-push for both platforms with the GHA cache), then `smoke-test` on `ubuntu-latest` and `ubuntu-24.04-arm` against `ghcr.io/<owner>/<name>@<digest>`. Only the digest crosses jobs: GitHub drops a job output containing a secret's value, and the image name contains the owner's name, which may be the Docker Hub username. Names come from the optional variables `IMAGE_NAME` (default `openinvites`) and `DOCKERHUB_NAMESPACE` (default the owner). `docs/releasing.md` lists all of it for the maintainer.
- **Docs:** `docs/operator/install.md` (first run, own proxy, trying it locally), `configuration.md` (every variable, grouped as `.env.example` is, with the operator/registration section and the Google and GitHub steps moved from README, SMTP, S3 with the IAM policy, rate limits and `TRUSTED_PROXY_HOPS`, legal pages via `compose.override.yaml`, analytics), `upgrade-backup.md` (upgrade, backup, restore, the password reset command, running notes including orphaned files). README's Configuration section is now a few lines linking them.

Decisions and things to know:

- **`OPERATOR_EMAIL` squatter recovery needs a session purge** (superseded by fix round 1, below: a reset now signs the account out everywhere). Better Auth's `revokeSessionsOnPasswordReset` is off (the default), so resetting the squatted account's password by email does not sign out whoever created it, and once the real holder verifies, that session belongs to the operator. `configuration.md` adds a step between the reset and the verification: delete the account's `session` rows with `psql` (checked by hand). The app-level fix would be `emailAndPassword.revokeSessionsOnPasswordReset: true` in `src/auth/auth.ts` (and the same in `scripts/reset-password.mjs`); left for the coordinator to decide, as it changes behaviour outside this ticket.
- **`docker compose restart` does not re-read `.env`**, so every doc says `docker compose up -d` after a change, except the no-mail `OPERATOR_EMAIL` promotion, which needs only a restart.
- **`.env` quoting**, tested with Compose 5.5.1: single-quoted values are kept exactly (`$` included, `$$` stays `$$`); in double-quoted or bare values `$$` becomes `$`; double quotes carry several lines; `MAIL_FROM=OpenInvites <no-reply@...>` needs no quotes. The docs recommend single quotes for the analytics snippet and files for the legal pages.
- **`.env` goes to the app whole** (`env_file`), so the Compose-only values (`POSTGRES_PASSWORD`, `COMPOSE_PROFILES`, `OPENINVITES_IMAGE`, `APP_PORT`) are in the app's environment too. Harmless; the password is in `DATABASE_URL` anyway.
- **QEMU for arm64**, as ruled. `next build` under emulation is slow (the publish job has 120 minutes), and emulated native toolchains occasionally crash; if that happens, building each platform on its own native runner and merging by digest is the usual fix.
- A missing `AUTH_SECRET` is caught by Compose here, but the app itself does not check it at start (Better Auth only refuses its default secret on first use). Outside this ticket's scope; noted.

**2026-09-24, implementing agent, review fix round 1.** The review found the missing session revocation was not only the `OPERATOR_EMAIL` squatter's edge case: for any host, someone holding a live session kept it after the owner reset the password, by email or with the operator command. Lint, type check, 319 unit tests, `e2e/host-accounts.spec.ts` (23 tests, 2 of them new or extended), the full browser suite against the rebuilt Compose `test` profile, and `deploy/smoke-test.sh` against a freshly built local image pass.

- **Reset by email:** `emailAndPassword.revokeSessionsOnPasswordReset: true` in `src/auth/auth.ts`. Better Auth deletes every session of the account after setting the new password, the resetting browser's own included, so that browser lands on `/sign-in?passwordChanged=1` and sees "Your password has been changed. Sign in with the new one." (before, a signed-in browser was bounced from there to the dashboard and never saw it). Sessions live in the database with no cookie cache, so revocation is immediate.
- **Operator command:** `scripts/reset-password.mjs` sets the password and deletes the host's `session` rows in one transaction, and says "They have been signed out everywhere." before its advice. The failure messages are unchanged, so `deploy/smoke-test.sh`, which matches "No host has the email ...", needed nothing.
- **Docs:** the `psql` purge is gone from `configuration.md`; the squatter recovery is reset by email (which signs whoever created the account out), then verify. The Mail section and `upgrade-backup.md`'s reset section say a reset signs the host out everywhere, with the command's new output.
- **Browser tests** (`e2e/host-accounts.spec.ts`): new, "resetting a password by email signs the host out on every device, the one that reset it too": signed in on two devices, the host resets by email on one, lands on sign-in with the message, the other device's dashboard sends it to sign-in, and the new password signs in. Extended, the operator-command test: the host stays signed in while the operator runs the command, the output says they were signed out, and their dashboard then sends them to sign in. Both failed against the image without the fix (dashboard instead of sign-in; the old output), and a mutant script that printed the new line but kept the sessions failed the extended test at its sign-in check.
