# 03: Videos: processing makes every size an event asks for, and a video is ready after the first

**What to build:** Processing makes each size the event ticks when M7's rule says a copy is needed at that size, skips a size that would come out the same as one already kept, and never upscales. A video is ready as soon as it can play: only the one copy an original that is not H.264 needs is made before that. The other sizes follow as `sizes` jobs, one encode per claim, behind every new upload; a size that fails is dropped and logged and the item stays ready. The pure size rules (what is made, what is missing, the labels, the list of an item's sizes) are written here for the player of ticket 06.

## Notes for the implementer

- **(plan)** "Skipped when it would be the same size as one already made" compares a size's side with the copies kept or chosen, never with the original: an H.264 original far over 1080p's bit rate still gets a lighter 1080p copy.
- **(plan)** A `sizes` job carries no list. Each claim works out what the item lacks from its event's sizes at that moment, so a host's change counts for what is made afterwards, and a copy the event no longer asks for stays. The smallest missing size is made first, so the size a slow connection needs never waits behind a long 4K encode (ticket 04). One failure drops the whole job; Make missing sizes (ticket 04) queues it again.
- **(plan)** The sizes after the first are made from the stored original, since the clip as sent is deleted once the item is ready; the original holds the same frames.
- `video_job.photo_id` stays unique: an item has one job at a time, and a `process` job turns into its `sizes` job.
- Which job is claimed first is not observable in a browser test; it is the `order by` above, and the review checks it.
- `madeBeforeReady`'s body differs from the plan's shared line only for an empty list, by ticket 02's ruling.
