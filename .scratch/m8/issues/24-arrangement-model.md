# 24: Sections: an event's arrangement is a pure model, and every section kind is in one registry

**What to build:** The rules of a page the host arranges, with no screen yet. An arrangement is the order of an event page's sections and, per section, whether it is on (where that is the arrangement's to say), collapsed, renamed or drawn in a style, plus the content of the host's Notes and Links. Absent means never arranged, which places each layout's sections exactly as today. A registry names every kind of section and what the Arrange sheet may change about it, and declares the shape a section's drawing takes, which ticket 25 fills. Everything here is pure and unit-tested; nothing is stored or drawn.

## Notes for the implementer

- **(plan)** The registry is two halves. `REGISTRY` (here) is what a section is called, what it offers and its icon, and is read by the Arrange sheet, a client component. What a section loads and how it is drawn is a server matter: ticket 25 registers each kind's `SectionDrawing` in `src/themes/sections/drawings.ts`, typed by this ticket. One file holding both would put server loaders behind `@/sections`, which client components import.
- **(plan)** `move` names the neighbour the sheet shows (`past`) instead of a step of one, so a section hidden from the sheet (the album where the site has it off) never swallows a press.
- **(plan)** The guest list's "who sees it" stays a column and moves to Arrange as the `audience` change; switching Who's coming on gives `afterReply`, the default.
- **(plan)** `parseArrangement` inserts a missing built-in by the Poster order, since it takes no layout; this only arises when a later version adds a kind.
- Countdown is last in every default order so that ticket 25's delays `[200, 200, 300, 300, 300, 400, 400][min(index, 6)]` reproduce today's on the Poster.
- `sectionId` uses `crypto.getRandomValues`, present in Node and the browser.
