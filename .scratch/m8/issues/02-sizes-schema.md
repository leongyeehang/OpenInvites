# 02: Videos: an item keeps several sizes, and the host ticks 1080p and 720p

**What to build:** A video can now keep more than one lighter copy, each a size named by its height: 4K (2160p), 1080p and 720p. The database learns the sizes an item has and the sizes each event asks for, and the host's Album settings offer two checkboxes, 1080p and 720p, both ticked by default, in place of 0.7's single "Lighter copy" choice. An event that chose 720p in 0.7 keeps 720p alone. Processing still makes at most one copy until ticket 03, and the player keeps working on the item's sizes until ticket 06 rebuilds it.

## Notes for the implementer

- **(plan)** 2160p joins the stored sizes through a new enum type, `video_size`, created with all three values in the migration that first uses it, as 0049 created `video_quality`. M7's rule forbids using a value in the migration that adds it to an existing enum; a new type has no such limit, so no value is ever added to an existing enum and the old type is dropped.
- **(plan)** A host may tick neither size. An original that is not H.264 then still gets one 720p copy before it is ready, so it plays in every browser; the hint says so. Ticket 03 carries this rule in `madeBeforeReady`.
- **(plan)** The 4K copy's bit rate is set here because `TARGET_BITRATE` covers every stored size: 16 Mbit/s with a 32 Mbit buffer, at most about 115 MB a minute (16,000,000 / 8 × 60 bytes). Ticket 04 makes it.
- The interface says "size", never "quality" or "resolution" (the spec's glossary proposal). The player's "Lighter copy" and "Original quality" stay until ticket 06.
- `video_job` rows from 0.7 are untouched: a 0.7 job still processes under the new code.
