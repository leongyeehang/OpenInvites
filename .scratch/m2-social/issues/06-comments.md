# 06: Comments

**What to build:** Guests who have replied, and the hosts, comment on the event page. A guest who has not replied sees the count and that replying opens them. A guest deletes their own; hosts delete any. Hosts are emailed on each comment, with a switch. Comments can be turned off per event.

**Blocked by:** 05 Co-hosts

**Status:** done

- [x] `src/comments/`: `comment.ts` (parse: 1 to 1000 characters, trimmed, line breaks kept; 500 per event cap), `visibility.ts` (`commentsView(viewer)`: `open` for a host or a guest with an RSVP on this device, `locked` otherwise; pure, unit tested), `repository.ts`, `actions.ts` (post as guest, post as host, delete with the rule: a guest deletes their own, a host any).
- [x] A `comment` rate limit: `RATE_LIMIT_COMMENT`, default `30/10m`, counted by the post action, with the "too fast" refusal the RSVP form uses.

The host's own name comes from their session; a guest's from their RSVP on this device.

How it landed:
- **Schema** (`drizzle/0019_comments.sql`): `comment` (id, `event_id` not null cascade, `rsvp_id` cascade, `host_id` referencing the account, cascade, `body`, `created_at`) with the check `comment_one_author`, `(rsvp_id is null) <> (host_id is null)`, and an index on each of the three foreign keys (the event's like every other table's; the RSVP's and the host's so the two cascades find their rows by index). `event.comments_enabled` and `event.notify_on_comment`, both default true; the generated SQL is hand-edited with `UPDATE "event" SET "comments_enabled" = false, "notify_on_comment" = false` after the columns are added. On the dev database all 8,488 existing events read false for both after it ran.
- **`src/comments/comment.ts`**: `parseComment(posted)` turns CR LF into one line feed, trims, then requires 1 to 1000 characters (`bodyRequired`, `bodyTooLong`); `roomForAnother(posted)` is the 500 cap (`MAX_COMMENTS`); `mayDelete(viewer, comment)` is the delete rule: a host any, a guest only a comment whose `rsvpId` is their RSVP's.
- **`src/comments/visibility.ts`**: `CommentViewer` is `{ kind: "host" } | { kind: "guest"; rsvpId } | { kind: "visitor" }`. `commentsView(viewer)` is `locked` for a visitor and `open` otherwise. `takesComments(event, viewer)`: comments on, viewer not locked, event not cancelled, and on a draft only a host (only hosts see a draft). The types the layout takes, `ShownComment` (id, name, byHost, body, createdAt, deletable) and `CommentsShown` (`{ view: "locked", count }` or `{ view: "open", comments, canPost }`), live here too.
- **`src/comments/repository.ts`**: `listComments` (oldest first, `created_at, id`, the name `coalesce(rsvp.name, user.name)`, read at display time), `countComments`, `createComment` (the event row `FOR NO KEY UPDATE` while the comments are counted, as announcements do; null when full), `findComment` and `deleteComment`, both scoped to the event.
- **`src/comments/actions.ts`**: `postCommentAction(slug, state, formData)` consumes `comment` first, before anything is looked up (as `saveRsvpAction` does), then finds the event by slug and who is commenting: a signed-in host the gate finds the event for (`findHostEvent`) whose role `can(role, "comments")`, else the guest whose RSVP is on this device, under its name. A host with an RSVP on the device comments as a host. Anyone `takesComments` refuses gets `closed`; then the parser's error, `tooMany` at the cap, or the comment is posted, the hosts notified, and `/e/<slug>` revalidated so the page is drawn again with it. `deleteCommentAction(slug, id)` finds the viewer the same way and the comment, applies `mayDelete`, and deletes; anything refused is left alone, as a missing comment is. Refusals are codes (`CommentRefusal`), turned into sentences in the browser under `EventPage.comments.errors`, as the RSVP flow does.
- **`src/comments/notify-hosts.ts`**: `notifyHostsOfComment(event, { name, body, hostId })`, a sibling of `notifyHostsOfRsvp`: `notifyOnComment` and `isMailConfigured()` first, `Mail.comment` in `event.locale`, one row per host from `eventHosts` except the one whose id wrote it, `queueMail`, `after(kickMailWorker)`, all inside a catch that logs `Mail: could not queue the hosts' email about a comment on event <id>`. Not a shared helper with the RSVP one: what they share is five lines of plumbing, while the rule, the exclusion, the values and the link differ, and folding them together would rewrite ticket 01's tested code for little.
- **Rate limit**: `comment` in `LimitName` and `LIMITS` (`RATE_LIMIT_COMMENT`, default `30/10m`), with `config.test.ts` extended. The refusal is the RSVP form's sentence, "You’re going too fast. Try again shortly.", in a `role="alert"` under the box, and the text stays.
- **Event page**: `page.tsx` builds the viewer from what it already had (`isHost`, `mine`) and loads `commentsFor(event, viewer)` in its `Promise.all`: nothing when comments are off, only `countComments` when locked (so a guest who has not replied is sent no comment at all), else the list with `deletable` from `mayDelete` and `canPost` from `takesComments`. It hands `PosterLayout` the data as `comments` and the form as a slot, `commentForm={<CommentForm slug=… />}`.
- **Poster layout**: a Glass card after the guest list, `SectionLabel` "Comments" with a speech-bubble icon. Locked: "{count} comments" (`=0` "No comments yet", `=1` "1 comment") and "Reply to join the conversation" with a lock, as the guest list's locked line. Open: an `<ol>` (or "No comments yet" when empty), each item the name, a "Host" pill in the accent where the host wrote it, the time (`formatMoment`, the event's zone, the viewer's locale, as announcements), Delete where allowed, then the body `whitespace-pre-wrap break-words`; then the form when `canPost`. Delete opens an `AlertDialog` ("Delete this comment?", "It comes off the event page for everyone.", "Delete it", "Never mind") whose form posts `deleteCommentAction`, rendered on the server exactly as the announcements page's.
- **`src/app/e/[slug]/comment-form.tsx`**: the client form: a labelled textarea ("Add a comment", `maxLength` 1000, `required`) whose text is React state, cleared once posted and kept on a refusal, and "Post".
- **Event form**: "Comments" (with the hint "Guests who have replied, and the hosts, can comment on the event page.") and "Email me when a guest comments", after the reminders setting, both ticked for a new event; `parseEventForm`, `EventInput` and both save actions carry them.
- **Messages**: `EventPage.comments` (title, count, locked, host, label, post, delete and its dialog, errors), `Mail.comment.{subject,body}` ("Priya Nair commented on Ada’s birthday"; the body is who, the text as written, "The event page:" and the link, and how to turn the emails off), `Events.form.{commentsEnabled,commentsEnabledHint,notifyOnComment}`. All in `en.json`, `zh-Hans.json` and `zh-Hant.json`.

Decisions and things to know:
- **Data to the layout, the form as a slot.** The brief asked for the comments and the viewer's standing as props, so the layout takes `CommentsShown`. Nothing under `src/themes/` imports from `src/app/`, and the page's client pieces reach the layout as slots (`rsvp`, the Design drawer), so the form does too; the layout shows it only when `canPost`. The delete confirmation needs no client component of its own: it is the announcements page's server-rendered `AlertDialog` with the action bound, inside the layout.
- **One post action, not two.** "Post as guest" and "post as host" are the two branches of `postCommentAction`, which decides who is posting on the server, the way the page does; the browser never says which it is.
- **Hosts can comment on a draft.** The ticket hides the form only on a cancelled event, and only hosts see a draft, so `takesComments` lets them; the comments stay once it is published. Notifications go to the other hosts as on any event.
- **Deleting stays possible** on a cancelled event, and through a crafted request on an event with comments off (no page shows Delete then). Neither is refused, since the comment is the author's or the host's to take back.
- **Every post counts, hosts' included**, before the event is looked up. A guest's post also draws the page again, which counts against `RATE_LIMIT_EVENT_PAGE` as an RSVP's redraw does; a host's does not (the page's existing exemption).
- **The rate-limit test's environment.** Neither the Compose dev and test profiles nor `.env.development` set `RATE_LIMIT_COMMENT`, so the test runs against the default 30/10m, and I left them that way. One guest posts 30 and the 31st is refused. In those profiles `RATE_LIMIT_EVENT_PAGE` is 40/1m, and that test's address uses about 34 of it (the host's visit to set the RSVP style, the guest's visit, the reply's redraw, 30 post redraws, a reload): under, but close, should anyone add steps to it.
- **Names are read when the page is drawn**: a guest who renames their RSVP renames their comments, and a host who changes their display name renames theirs. A co-host who is removed from the event keeps the "Host" mark on what they wrote then (the comment still belongs to their account); deleting their account removes their comments.
- **"No comments yet"** stands for a count of 0 in both states (the ICU `=0` branch), so an open section with nothing in it, such as a cancelled event nobody commented on, is never an empty card.
- The mail footer names "Email me when a guest comments" even when the comment was another host's; the setting covers both.
- After a delete the comment, and the dialog with it, leave the page, so focus falls to the document, as on the announcements page.
