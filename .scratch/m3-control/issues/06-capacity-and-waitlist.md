# 06: Capacity and the waitlist

**What to build:** A host sets a capacity, counted as the headcount is. Going replies that do not fit are waitlisted in order and promoted automatically when space opens, with an email when the guest gave one. One pure rule and one transaction decide every reply from now on.

**Blocked by:** 01 Operator limits (the replies check moves into the transaction), 03 The custom link (`eventPath` in the mail)

**Status:** done

- [x] Schema: `event.capacity integer` (nullable); migration 0028 adds `waitlisted` to `rsvp_status` with `ALTER TYPE ... ADD VALUE` and nothing else; migration 0029 adds `rsvp.waitlisted_at timestamptz` and `rsvp.promoted_at timestamptz`. `RSVP_STATUSES` stays the three a guest can choose; a new `SAVED_STATUSES` adds `waitlisted` where the stored status is typed.
- [x] `src/rsvps/admission.ts` (pure, unit tested), the signature later tasks rely on:
  `type Wanted = "going" | "maybe" | "cant"`; `type Approval = "approved" | "pending" | "declined"`;
  `type AdmissionInput = { approvalRequired: boolean; capacity: number | null; headcount: number; invited: boolean; wanted: Wanted; party: number; current?: { status: SavedStatus; approval: Approval; party: number } }` where `headcount` is the approved Going replies other than this one, with their plus-ones, and `party` is the guest plus their plus-ones;
  `type Admission = { status: SavedStatus; approval: Approval } | { refused: "capacityFull"; placesLeft: number }`;
  `admit(input): Admission`. In this task `approvalRequired` and `invited` are accepted and ignored and `approval` is always `approved` (task 7 makes them real). Rules: `maybe` and `cant` are saved as asked; `going` with no capacity is `going`; a current approved `going` reply asking `going` fits when `headcount + party <= capacity`, else is refused `capacityFull` with `placesLeft = capacity - headcount` (a Going guest keeps their place; the refusal is for raising plus-ones); a current `waitlisted` reply asking `going` stays `waitlisted` (promotion decides, in order); any other reply asking `going` is `going` when it fits and `waitlisted` otherwise.
- [x] `src/rsvps/waitlist.ts` (pure, unit tested): `promotable(waitlist: { id: string; party: number }[], space: number): string[]` walks in order and stops at the first party that does not fit.
- [x] The transaction (`src/rsvps/repository.ts`): `saveRsvp`, `editRsvpAsHost`, `deleteRsvp`, and `updateEvent` when the capacity changes, each lock the event row `FOR NO KEY UPDATE`, compute the headcount excluding the reply being written, call `admit` (a host's edit sets the status the host chose without `admit`: a host's edit is never refused by capacity), write, then `promoteWaitlist(eventId, tx, now)`: `promotable` over the waitlisted replies in `waitlisted_at` order against the space left, each promoted row set to `going` with `waitlisted_at` null and `promoted_at` now, and one mail per promoted guest with an email queued inside the transaction with `queueMail(rows, tx)` (`Mail.promoted.{subject,body}` through `guestMails`: "A place opened up: you're going to {title}", when, where, the event link by `eventUrl`, the footer), then `after(kickMailWorker)`. Task 1's replies-per-event check moves inside the lock. The spec's rule: no later task writes an RSVP any other way.
- [x] Refusal `capacityFull` → `Rsvp.errors.capacityFull` "Only {count} places left.", mapped to the plus-ones step.
- [x] Event form: a **Guests** group (above the contact details) with "Capacity" (number, 1 to 5000, blank for none; hint: "Counts guests who say Going and their plus-ones, as the headcount does. Maybe doesn't count. Leave empty for no limit. This instance takes up to {max} replies per event."). `parseEventForm`, `fields()`, `duplicateInput`.

## Notes for the implementer

- `editRsvpAsHost` already runs a transaction with a row lock; it shows the shape. Lock the event row first, then the reply, the order `removeEvents` takes.
- Adding an enum value and using it cannot share a transaction in Postgres; hence two migrations.
- Commit subject, e.g. `Capacity: a full event waitlists Going replies and promotes them in order`.

Decisions and things to know:
- `admit` keeps a Going guest Going when their party is no larger than before, even past a capacity lowered below the headcount; only a party raised past the room left is refused. The ticket's rule read literally ("fits when headcount + party <= capacity, else refused") would refuse a Going guest's name change on an event whose capacity the host lowered; its parenthetical ("a Going guest keeps their place; the refusal is for raising plus-ones") and the spec ("nobody is moved to the waitlist by it") rule. `placesLeft` is floored at 0, and `Rsvp.errors.capacityFull` is plural: "No places are left." / "Only 1 place left." / "Only {count} places left.".
- A host saving a waitlisted guest's row with the status select at Going (the select shows Going for them, which they asked for) keeps them on the waitlist in their place (`hostStatus`); the host promotes with Move to Going. Any other status the host picks is set as chosen, over capacity included.
- Move to Going is a promotion made by hand: Going at once with `promoted_at`, the guest emailed "A place opened up" when they gave one, and the hosts emailed "…is now Going" as for any change a host makes (`editGuestAction` already tells every host of a host's edit). It runs in the same transaction shape; it does not run `promoteWaitlist`, since taking a party off the waitlist into Going can only leave less room.
- The hosts' notice reads "{name} is on the waitlist for {title} (party of {party})", the ticket's words with the event named as every other notice subject does; `Mail.rsvpReply.status.waitlisted` is "Going (on the waitlist)", used when a waitlisted RSVP is removed ("It said Going (on the waitlist).").
- Headcount copy: "{count} of {capacity} people expected", following the existing "N people expected"; it reads "1 of 1 people expected" at a capacity of one.
- A waitlisted guest at the front who lowers their own party until it fits is promoted by their own save and confirmed Going in the same response; by the ticket's rule (saved Going, asked Going, previous not Going) confetti falls then. The spec's "not on a promotion" is read as the automatic promotion that happens while the guest is away.
- `repliesAtLimit` reads the instance settings through the transaction, not the per-request cached `instanceLimits()`, so a transaction holding the event lock never waits for a second pool connection that replies queued behind it may hold.
