# 08: Personal invite links

**What to build:** A host makes a link for a named guest. Opening it fills the name (and the email, taken as proven) and ties the reply to the invite; the link then works as the guest's edit link. The host sees who opened and who replied.

**Blocked by:** 07 Approval (an invited guest is approved), 05 The email proven by a code (an invite's email counts as proven)

**Status:** done

- [x] Schema: `invite` (`id`, `event_id` cascade, `name text not null`, `email text`, `token text not null unique` (24 characters of `SLUG_ALPHABET`, stored in clear as `rsvp.mail_token` is, because the host may see it again), `created_at`, `opened_at timestamptz`, `rsvp_id` references `rsvp` on delete set null); `rsvp.invite_id` references `invite` on delete set null. Migration 0031.
- [x] `src/invites/invite.ts` (pure, unit tested): `MAX_INVITES = 500`, `parseInvite({ name, email })` (name 1 to 80 characters trimmed, email optional by the RSVP rule), `generateInviteToken()`, `inviteState(row)` → `notOpened`, `opened`, `replied`. `src/invites/repository.ts`: `createInvite`, `listInvites(eventId)` (newest first, with the reply's status when any), `findInviteByToken`, `markInviteOpened`, `deleteInvite`, `countInvites`.
- [x] `/events/[id]/invites` (hosts with `can(role, "guests")`; "Invites" in the manage page's buttons row after Guests): a form Name, Email (optional), **Make link**; the list: name, email, the state badge (Not opened, Opened, Replied with the status), the link `/i/<token>` with Copy while unanswered, Delete behind an `AlertDialog` saying the link stops working and a reply made with it stays. At 500 the form is replaced by a sentence. Keys under `Invites.*`.
- [x] `/i/[token]` (`src/app/i/[token]/route.ts`): an unknown token is the not-found page; a known one records `opened_at` the first time; when the invite has a reply, the route sets the reply's device cookie to the invite's token and redirects to the event page; otherwise it sets a cookie `invite_<eventId>` holding the token (thirty days, httpOnly, the RSVP cookie's options) and redirects to the event page. The proxy's matcher gains `/i/:path*`, counted against `eventPage`, and `notFoundHere` renders unknown tokens whole.
- [x] The reply through an invite: the event page, when the device has no reply and an invite cookie names a live invite of this event, passes `flow.invite = { name, email }` and every layout fills the name (editable) and the email; `saveRsvpAction` reads the cookie, verifies the invite belongs to the event and has no reply, and saves with `rsvp.invite_id`, the invite's token as the reply's edit token (`edit_token_hash = hash(token)`, so the confirmation's edit link is `/i/<token>` and `/r/` is not shown), `emailVerifiedAt` set when the email equals the invite's (`needsCode` is false then), and `admit(..., invited: true)`; the invite records `rsvp_id`. A device that already has a reply ignores the invite cookie.
- [x] Host guest list: an **Invited** section at the bottom listing invites without a reply (name, email, Opened or Not opened); invites count in no count.
- [x] Deleting an invite unlinks its reply (`rsvp.invite_id` null; the reply and its edit token stay, the device cookie keeps working) and the link stops working.
- [x] Unit tests: `parseInvite`, `inviteState`, the token's shape.
- [x] Browser tests (`e2e/invites.spec.ts`): the host makes an invite for "Mei Lin" with an email and sees Not opened; a guest in a fresh context opens the link, sees the name filled in and the email filled in, and the host's list reads Opened; the guest replies Going, the confirmation's edit link is the invite link, the host's list reads Replied · Going and the Invited section no longer lists them; with approval on, an invited guest's reply is approved at once (the guest list opens for them); with the email check on, an invited guest with the invite's email meets no code step; a second context opening the invite link lands on the reply and can change it; the host deletes the invite and the link is not-found; the Invited section shows an invite nobody opened.

## Notes for the implementer

- `/r/[token]/route.ts` is the model for `/i/`: it sets the cookie and redirects.
- The invite's token doubles as the reply's edit token on purpose (spec, "Personal invite links"); a reply made from the event link keeps its own random edit token.
- Commit subject, e.g. `Invites: a host can make a personal invite link for a named guest`.

Decisions and things to know:
- The rulings as given: migration 0033; the Invited section apart from `GROUPS`; duplicates copy no invites (nothing to change: `duplicateInput` builds a new event); the route adds no state rule (a draft's or a cancelled event's invite still records the opening and lands on the page the state shows); a deleted invite's reply keeps its token and shows its `/r/` link; a device with a reply ignores the invite cookie; an answered invite on a new device sets the RSVP cookie; `opened_at` the first time only; the token in clear, 24 characters (the spec's "24 random bytes, stored hashed" is superseded by the ticket and the ruling).
- "A live invite" is read as: of this event, not deleted, and nobody has replied through it. A device whose invite was answered from another device since gets no prefill and replies as a plain guest (pending if the event asks for approval); only the invite link itself takes a device to the reply.
- An invite deleted or answered from another device between the page and the save is refused under the lock as `closed` ("This invitation is not taking RSVPs."); otherwise the save would insert a second RSVP with the same edit token hash (unique) or one tied to nothing, and an email taken as proven by an invite that no longer holds would skip the code. A reload then shows the plain page. Not browser-tested (a race).
- The invite's email is filled in and saved only when the event asks for an email; with Email "Don't ask" the reply has none, so a guest is never emailed about an event that did not ask them for an address. The email comparison is exact after trimming, as the code rule compares (a change of case means a code when the event checks emails).
- The proof applies whenever the email equals the invite's, the email check on or off, so the host's tick shows on that address either way.
- The Invited section shows once the event has any invite, as the Waitlist shows once it has a capacity; with everyone replied it reads "Invited (0)" and "Nobody.".
- The invites page does not refresh itself (the guest list does); "Opened" shows on the host's next load.
- A link preview fetched by a chat app counts as an opening and gets the cookie; nothing to do about it short of a click-through page.
- Copy only (the ticket); the spec's "or through the share sheet" is not offered on the invites page.
- `Events.manage.duplicateHint` still lists "Replies, comments and announcements" as not copied, without invites; left for the maintainer (ticket 11).
